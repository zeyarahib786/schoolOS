# Build and deployment guide

Use [Local setup](local.md) for local installation, database initialization, and demo accounts. This guide describes how the current build is configured; AWS resource names and deployment credentials are not stored here.

## Build the frontend

From the repository root:

```bash
npm --prefix client ci
VITE_API_BASE_URL=https://api.schoolos.solvagence.com/api/v1 npm --prefix client run build
```

This produces `client/dist/`. The API URL is a public browser setting, embedded during the build. Changing an environment variable on the hosting server after building will not rewrite the files. A bare build can inherit the localhost value in `client/.env` or the Dockerfile default; explicitly set the intended deployment value.

Deploy the **complete** output directory, including `index.html`, the hashed React bundle, `schoolos-runtime-*.js`, and the copied CSS/static assets. The runtime bundle is generated by `client/build/runtime.ts` using the execution order in `client/src/features/registry.ts`. Uploading only the main `index-*.js` file will break startup.

For local inspection of the output:

```bash
npm --prefix client run preview -- --host 127.0.0.1 --port 5176
```

The preview server is a build inspection tool. Use the configured production static hosting service or Nginx for deployment.

## Hosting layouts

| Layout | Frontend build setting | API setup |
|---|---|---|
| Docker Compose | `/api/v1`, supplied by Compose | Nginx proxies `/api/` to the `api` service |
| Separate static hosting and API domains | Public HTTPS API URL | API CORS must allow the frontend's exact HTTPS origin |
| Same-origin reverse proxy | `/api/v1` | Hosting must explicitly forward `/api/` requests to the API |

The project's public frontend/API domains used for live checks are `https://schoolos.solvagence.com` and `https://api.schoolos.solvagence.com`. The October 8, 2026 live inspection observed an S3 response behind CloudFront with Brotli compression. This observation does not establish the account's infrastructure configuration or provide an automated deployment path.

When serving static files through S3/CloudFront or another host, configure SPA route fallback and content types. Cache hashed JavaScript assets, while letting browsers obtain the current `index.html`. The copied `assets/css/` and original `assets/js/` paths are not content-hashed; replace/invalidate changed stable paths as appropriate. The checked-in Nginx configuration gives hashed build assets a one-year cache lifetime. HTML and stable copied asset paths revalidate. Gzip is enabled for text, JavaScript, CSS, JSON and SVG; CloudFront compression must be configured on the actual distribution.

Publish new assets before switching the entry HTML, keep assets referenced by still-cached HTML available, and refresh/invalidate cached entry HTML after publishing. Verify the public URL references the new runtime asset; committing source code does not update already-hosted output.

## Build and run the API

```bash
npm --prefix server ci
npm --prefix server run build
npm --prefix server start
```

`npm start` loads `server/.env`; the Docker image instead runs `node dist/server.js` with container-provided environment variables. Configure:

- `NODE_ENV=production`, `PORT`, and `API_PREFIX` (normally `/api/v1`).
- `MONGO_URI` for the intended MongoDB replica set.
- Different random `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` values of at least 32 characters.
- `CORS_ALLOWED_ORIGINS` for the public browser origin(s).
- Rate-limit and database-pool settings appropriate to the running environment.

The API connects to MongoDB before listening. `/health` reports process status; `/ready` reports the database connection state. A database-backed deployment check should include `/ready`.

The server image is built in two stages and runs as an unprivileged user with production dependencies. The frontend image serves the built assets through Nginx. Building the frontend Dockerfile directly requires an explicit API build argument:

```bash
docker build --build-arg VITE_API_BASE_URL=/api/v1 -t schoolos-web ./client
docker build -t schoolos-api ./server
```

The frontend's bundled Nginx configuration expects a resolvable `api:4000` upstream. Compose supplies it; a standalone container requires equivalent networking or an adjusted proxy configuration.

## Optional external delivery and signed school PDFs

These integrations stay disabled until the school supplies its provider and authorized signing identity. Never put server keys in `VITE_*` variables or commit `.env`, `.p12`, `.pfx` or passwords.

Email uses Resend. Set `NOTIFICATIONS_ENABLED=true`, `RESEND_API_KEY`, and a verified `RESEND_FROM_EMAIL` in the server's secret configuration. Configure the Resend webhook endpoint `/api/v1/notifications/resend-webhook` with `RESEND_WEBHOOK_SECRET`; enable delivered, bounced, complained and failed events. The endpoint verifies the original raw payload using Svix signatures. See [Resend email API](https://resend.com/docs/api-reference/emails/send-email) and [webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests).

SMS provider selection is deferred. Leave `SMS_PROVIDER=disabled`. An optional AWS SNS adapter accepts `aws-sns`, `SMS_AWS_REGION`, optional `SMS_SENDER_ID` and `SMS_MAX_PRICE`. AWS credentials use the standard SDK credential chain; authorize only required SNS publishing and configure the destination region/sender with the provider before enabling. A provider acceptance is not a delivery confirmation. No live SMS delivery was verified.

The API process runs a durable database-backed worker. Teacher requests await Administrator/Principal approval. Recipients must have active school accounts; SMS requires a linked international E.164 profile phone. Worker claims prevent two workers sending the same pending job. Unknown outcomes require review; ambiguous SMS outcomes cannot be retried through the API. Email retries reuse the Resend idempotency key and stop before its 24-hour expiry. Stale in-flight jobs become Unknown rather than silently being sent again.

Set `PDF_SIGNING_P12_PATH` to a privately mounted school-authorized RSA PKCS#12 file and `PDF_SIGNING_P12_PASSPHRASE` through server secrets. Ensure the unprivileged API user can read the mount; never expose it through public uploads. The signer checks key/certificate matching, current validity and digital-signature key usage. Administrator/Principal creates signed issued records; authorized family users can download existing signed copies. Unsigned PDFs remain available independently. Store and back up the `CertificatePdf` collection with the database because it holds the immutable generated bytes and SHA-256 hashes.

The generated detached CMS PDF signature protects covered bytes. Whether a PDF reader trusts the identity depends on the school's certificate chain and recipient trust configuration. Timestamp authority, long-term validation, revocation checking and public QR verification are not implemented. Local tests use an ephemeral self-signed fictional certificate solely to verify the cryptographic signature and tamper rejection; it is not a school signing identity.

PDF fonts live under `server/assets/fonts/`, including the OFL license. Docker copies these assets alongside `dist`. `PDF_FONT_PATH` may override the bundled font with a school-approved Unicode font.

The API now uses native OpenSSL for PKCS#12 parsing and detached CMS signing. Install OpenSSL 3 in non-Docker runtime environments; the server image installs it. Private keys/passphrases never enter command arguments, temporary signing files use restricted permissions and are removed. The Forge and Forge-based signer dependencies were removed. Fresh backend and frontend dependency audits report zero vulnerabilities. Native cryptographic verification and tamper rejection passed locally; school-authorized certificate setup remains deferred.

## Backup and restore operations

Prefer managed database point-in-time recovery for live writes. The supplied scoped archive command is a **maintenance-window backup**: stop every API instance, notification worker, import job and other database writer first. It compares complete source document/index fingerprints before and after the dump and rejects a changed source. This comparison does not replace a write freeze or a managed consistent snapshot.

Install the official [MongoDB Database Tools](https://www.mongodb.com/docs/database-tools/installation/). The commands use `mongodump --archive --gzip` and `mongorestore` namespace mapping; see [MongoDB restore documentation](https://www.mongodb.com/docs/database-tools/mongorestore/). The backup command encrypts the stream using AES-256-GCM, writes files with mode `0600` and records collection hashes/counts/indexes in a private manifest. Connection credentials are supplied through a temporary restricted configuration file rather than process arguments.

Store a separate random, base64-encoded 32-byte `SCHOOLOS_BACKUP_KEY` in the operator secret manager. Losing it makes these archives unrecoverable. Store its recovery copy separately from the encrypted backups. Use a private encrypted filesystem/object store with an approved retention policy; no remote backup destination has been configured by these source changes.

```bash
# From server/, using a protected environment file outside the source tree:
# MONGO_URI, SCHOOLOS_BACKUP_KEY, SCHOOLOS_BACKUP_DB=schoolos,
# SCHOOLOS_BACKUP_WRITES_PAUSED=yes and optionally SCHOOLOS_DB_TOOLS_DIR.
node --env-file=/private/operator-backup.env scripts/backup.cjs backup /private/backups/schoolos.enc

# A separate environment file selects the recovery cluster and a NEW EMPTY target:
# SCHOOLOS_BACKUP_DB=schoolos_restore_drill
node --env-file=/private/operator-restore.env scripts/backup.cjs restore /private/backups/schoolos.enc
```

Restore refuses populated targets, production-style target names and the original source database name. It verifies the checksum and complete encryption tag **before database writes**, then verifies restored BSON records and indexes. Generated certificate PDFs and GridFS uploads are covered. Temporary plaintext is restricted and removed on normal completion/failure; use an encrypted operator filesystem and clean abandoned temporary files after an abrupt host failure. A failed database verification leaves the isolated target available for diagnosis; never point an API worker at that target until review is complete.

The isolated drill passed ten checks covering Arabic/BSON values, PDF bytes, GridFS, indexes and unsafe restore rejection. Run it regularly with [operations drills](../../tests-e2e/operations/README.md). A real production backup schedule, restore destination, retention period and school-approved RPO/RTO remain deployment decisions; this drill does not claim a backup of live data.

## Monitoring and graceful shutdown

`/health` checks process liveness. `/ready` performs a bounded database `hello` and requires a writable replica set or a mongos; disconnection, standalone MongoDB and shutdown return 503. Docker's API health check now uses readiness. Node shutdown stops new delivery claims, waits for the current delivery and HTTP connections, disconnects MongoDB and has a 30-second drain deadline. Configure the orchestrator stop timeout to exceed this deadline.

Every minute the API writes a structured `Operational metrics` log with request totals, 4xx/5xx totals, aborted requests, active requests, mean latency, a bounded p95 estimate and memory use. No URLs, student names, email addresses or tokens are used as metric labels. Existing request IDs correlate individual errors. Configure the actual AWS log collector and alarms after the deployment target is identified; JSON stdout alone does not create CloudWatch alarms.

Initial alarm policy for school review: readiness failures for two consecutive minutes, 5xx above 1% with at least 100 requests in five minutes, sustained p95 above 3 seconds, and memory above 80% of the configured container/host limit. Alert separately when a scheduled backup is missing or a restore drill fails. These are proposed thresholds, not measured service guarantees. Avoid alarms on expected role-denied 403s as though they were server failures.

```bash
node server/scripts/health-check.cjs https://api.schoolos.solvagence.com
```

## Release retention and rollback

For a filesystem/Nginx static host, the release helper keeps complete immutable snapshots, verifies file checksums and atomically switches a `current` symlink. Set the host's document root to `<release-root>/current`; this helper does not automatically alter a running host.

```bash
node client/scripts/static-release.cjs prepare client/dist /private/web-releases
# Use the ID emitted by prepare:
node client/scripts/static-release.cjs activate /private/web-releases RELEASE_ID
# Roll back by activating the previous verified ID with the same command.
```

Previous hashed assets survive a forward switch, and newer hashed assets also survive rollback for browsers holding cached newer HTML. Stable CSS and entry HTML come from the selected snapshot. Never manually overwrite a release directory. The local rollback drill passed nine checks, including corrupted-release refusal; it is not an AWS rollback exercise.

For S3/CloudFront, publish hashed assets before HTML, keep older hashed assets and snapshot the previous full release. Restore the earlier HTML and stable assets, then invalidate changed stable paths. For an API orchestrator, retain the previous image **digest** and task/service definition. Roll back to that exact definition and verify readiness and representative workflows. Do not automatically restore an older database on a code rollback: writes made since deployment must be preserved, and any schema/index migration needs its own compatibility plan.
